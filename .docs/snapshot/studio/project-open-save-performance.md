# Studio 打开工程、保存与曲线面板复核

本报告记录开发分支的配对实验。回移到 `release/studio-0.10.1` 时，外部面板按需创建该版本已有的曲线、音源和绑定编辑器。工程保存保留当前版本允许省略的空 `audio.defaultConversions`。文中默认滤波器、632 份文档和 676 项测试的数据均来自开发分支。[原始实验记录](https://github.com/xindong/harken-studio/blob/8c32dccc625917d876c24fbb21ff9a8a5b54322f/.docs/snapshot/studio/project-open-save-performance.md)

2026-11-27，Windows x64、Qt 6.8.3、RelWithDebInfo。对照版是上一轮已经优化过的 Studio，每个进程都使用桌面 `saga2_audio` 的一份新副本。工作区、362 份原始音频和 806 份对象文档均随副本保留。[第一轮数据与提交历史](project-edit-performance.md)

## 首次保存

对于已通过当前 Schema 校验的文档，缺省滤波器和显式默认滤波器得到相同的业务值，缺省的默认转换映射和空映射也等价。查看工程再按保存没有产生相关编辑。原先，打开时重新序列化得到的 631 个对象及一个根文档差异，却会触发一次 632 文件的事务。

本轮将这两项等价规则放在文档写出和已保存状态的比较处。同一编辑会话以原文档身份保留省略形式，因而编辑为非默认值会落盘，跨保存撤销也可恢复原先的省略。新对象沿用当前写入格式，显式默认和有效非默认保留。版本迁移继续通过原有的审批、安装和校验流程。文件格式中只有已确认等价的可选字段适用这个规则。

## 路由保存

更换一个 Sound 的输出 Bus 会改变路由，需要核验目标、父级、继承及 Bus 图。此前，文档中的整个字段组还参与了全局工程规则的输入，造成全部对象的身份和结构等规则重新计算。现在分别处理字段组业务校验、工程规则实际引用的字段和文档依赖，并更新新目标索引。准备及提交阶段仍按原读集检查磁盘内容。在单次核验中，同目录的祖先和实际拼写可共用，多个文档各自保留 SHA-256 核验。外部改写同长度字节并恢复原修改时间的依赖文件，两版都拒绝保存。

## 打开和试听

上轮版本的一次原生窗口探针中，启动时准备音频花了 803 ms，随后注册音频花了 732 ms。平台和语言到工程打开通知时才恢复，首次运行时同步已经完成，窗口呈现前再次准备音频又花了 791 ms。现在提交工程会话时先恢复其平台、语言与预览模式，恢复工作与首次运行时同步合并提交。一次常规加载沿用已完成的当前版本校验，执行过升级时重新校验实际安装的工程。

需要完整采样范围时，音频准备直接移交解码缓冲。首次注册尚无缓存、且调用者没有传入预期修订的 PCM，由引擎注册入口校验并返回内容修订。已缓存或带预期修订的调用保留对照。首次打开仍会准备可供引擎播放的媒体并等待就绪。播放中改音量、撤销和停止使用实时空音频输出验证，覆盖实际渲染和母线读数。

## 曲线编辑器

首次打开一条衰减曲线时，旧版同时构造滤波器、音源和绑定列表。单次插桩中，隐藏的滤波器构造占 66 ms，曲线绑定只占 2.7 ms。各编辑器现在在第一次选用时创建，随后复用，浮窗仍可固定、隐藏和恢复。四种内容的切换、三个曲线点、两对贝塞尔手柄、焦点和窗口尺寸均已核验。

六个独立原生窗口进程的绘制探针，按每版 3 个样本取中位数。打开命令发出到曲线画布完成首次绘制从 **280.1 降至 39.1 ms**。在同一面板重复打开为 13.8 → 13.5 ms，隐藏后重开为 34.7 → 36.9 ms。这组覆盖 Qt 实际绘制，测量时机器上有并行开发工作，分别保留了每个样本。

## 原生窗口对照

正式构建在同一台 Windows 机器上按前轮、本轮、本轮、前轮的顺序各启动两个新进程。文件缓存自然保留。下表取命令发出到主窗口 shell 返回成功的中位数，启动一项从创建进程计时。每个进程使用独立工程副本。

| 用户操作 | 每版样本数 | 前轮 ms | 本轮 ms |
| --- | ---: | ---: | ---: |
| 启动并打开，收到首个工程查询回复 | 2 | 4,465.69 | 3,355.12 |
| 打开原样工程后首次保存 | 2 | 2,497.31 | 28.36 |
| 后续空保存 | 6 | 29.64 | 28.40 |
| 修改一个声音的音量后保存 | 4 | 64.65 | 65.30 |
| 首次打开所选衰减曲线 | 2 | 163.27 | 33.05 |
| 移动 Action | 2 | 37.42 | 32.96 |
| 保存结构修改 | 2 | 289.87 | 252.89 |
| 常规编辑序列中，切为 Local 并赋值 Bus 后保存 | 2 | 248.45 | 273.51 |
| 路由专项中，切为 Local 并赋值 Bus 后保存 | 2 | 243.83 | 210.03 |
| 路由专项中，随后切换目标 Bus 并保存 | 10 | 145.75 | 103.78 |

常规序列先改音量、选择声音、设置 Conversion，再撤销和改路由。该序列的两次组合保存分别为 208.80 和 338.22 ms，能感到的长等待仍会出现。专项在同一 Sound 上交替选择 Battle 和 Hero，每次保存前逐文件取快照，再发一条工程查询，让主窗口处理已排队的更新。专项中的首次组合保存分别为 209.06 和 211.00 ms，后续十次落在 99.41–111.71 ms。赋值命令本身为 37.30 → 37.60 ms。两种序列均保留，用来区分连续操作中的延迟与单独保存的成本。以上计时的终点为成功回复，曲线绘制探针另测 Qt 画布完成时间，均未测量显示器呈现。

常驻 CLI 在独立工程副本上做了四轮相同顺序的交替对照。每版十次稳态路由保存为 252.68 → 168.42 ms，Bus 重命名后保存为 401.21 → 284.40 ms。对每次稳态路由保存，系统读操作中位数仍为 4,869。原生窗口专项的全部 24 次保存逐份核对 808 份文件的 SHA-256、大小与修改时间，只有所属声音的 VP 发生变化，读回的本地模式、目标 GUID 均正确。

## 行为复核与剩余开销

- **保存与升级。** 每个检查点都包含 806 份 VP、1 份 HSP 和 1 份资产注册表。已是 Schema 10 的原样副本首存由改写 632 份降至 0 份。将低通设为 4812 Hz 并保存只写了所属声音；保存后撤销、再保存恢复原文档的省略表示；重做恢复非默认值。独立进程重开、另存、结构保存以及 Schema 7、8、9、10 的历史文件均有复核，存储专项 52 项通过。
- **导出与播放。** 编辑前后各自强制导出 Windows 全部 Action。每次比较两个构建的 166 个运行时包和 166 份 JSON 元数据，两阶段共 664 对的 SHA-256 全部一致。这个案例中该声音的滤波器独立修改前后也得到相同的包。使用实时空音频设备播放、降音量、撤销、停止，核对了播放句柄、声部数和母线电平。物理音频设备和其他操作系统未实测。
- **打开。** 最终启动探针看到从首次同步到主窗口接受命令只有一轮媒体准备（688 ms）和一轮注册（402 ms）。前轮在同一位置分别为 803 和 732 ms，随后又准备了 791 ms。启动仍约 3.36 秒，首次试听可用的媒体准备和注册占其中约 1.09 秒。单次计时另将源淡变修正定位到 1 ms 以内。打开前的工程分析和事务恢复后的复核之间，文件可由外部工具改写；普通打开并未跨这个边界信任一次旧分析。
- **日常编辑。** 第一轮复核覆盖 Shared 与 Windows 的 Inherit/UseShared、数值拖动与撤销、曲线加点、拖点与手柄、树搜索和移动。第二轮针对这些编辑的首用和保存开销补测。音量保存、已打开的曲线再次显示、路由赋值本身未观察到进一步的稳定提速。路由与结构保存仍有约 0.1–0.3 秒的等待，包含外部冲突核验及主窗口更新。
- **工程原件。** 桌面工程与审计开始时的副本再次按相对路径比较，808 份工程数据和 362 份媒体的 SHA-256 全部一致。

## Windows 导出缓存

一轮全套测试中，下一次导出请求从缓存读到了外部改写前的音频散列。两个旧构建运行同一用例各 200 次，分别复现 1 次和 2 次。Windows 的本地文件 ID、长度、写入时间和变更时间可以在快速等长覆盖时同时相等。保持一次请求的音频快照有助于稳定出包，新请求需要识别写入后的文件版本。

本轮在 Windows 源文件的可复用凭据中加入文件系统变更日志 ID 和该文件的更新序号（USN）。卷无法提供可靠序号时，构建从锁定的输入读取实际内容并计算 SHA-256。已有缓存首次使用新凭据时重新核验一次。旧格式的 362 份源凭据在案例中全部重算，合计 1.97 秒。

| 独立进程中的检查 | 命中结果 | 正确性核对 |
| --- | --- | --- |
| 连续三次检查全部未改素材 | 每次 362/362 | 每次将 362 个缓存散列逐个与磁盘 SHA-256 对照 |
| 同路径等长覆盖一个 WAV 并恢复修改时间 | 361/362，随后再查 362/362 | 改过的 WAV 在新请求中取得新的内容散列 |
| 普通增量导出，所有源文件未改 | 两轮均 166/166 个包，0 次转换 | 新进程用时 0.672 和 0.644 秒，332 份输出的内容、大小和修改时间全部相同 |
| 编辑 Mus_Login.wav 的 1024 帧，恢复原修改时间再导出 | 两轮均 163/166 个包命中，3 个重建，1 次媒体转换 | 两轮各与一份相同输入的无缓存重建逐文件对照，每轮 332/332 一致；播放和停止 Mus_Login 的运行时包均确实变化 |

三次暖检查 362 份源凭据的中位数为 21.51 → 27.19 ms，计时只包含源文件识别。表中的导出计时还包含新进程启动和读取工程。专项测试涵盖同大小同时间的外改、新旧请求各自读到的内容，以及其他进程仍持有写句柄的情况。三个定向用例各重复 300 次，共 900 次通过。

在本机 NTFS 上分别模拟无法取得日志 ID、无法取得单文件 USN，两组各 7 项通过。探针从生成包逐帧读回修改后的音频，并将增量导出的包、清单、波形与强制导出逐字节比较。未在实际的 ReFS 和网络共享上测量性能。

导出修复后用同一正式 Studio 程序重跑了主窗口常规编辑序列。该次打开为 3.52 秒、原样首存为 29.78 ms，808 份数据文件的内容均保留。上文的主窗口配对表来自导出修复前的同一套编辑、打开和保存实现。最终 Studio 全套 CTest 为 **676/676 通过，0 跳过**。修复前的一次全套原始结果为 675/676，间歇失败和最终复验分别保存在 `open-save-review/final-tests.xml` 和 `open-save-review/final-verified-tests.xml`。

本机复核材料在 `.local/studio-performance-optimization/`。主窗口配对原始数据与启动阶段日志见 `open-save-review/`，路由专项在 `storage/routing/`，保存与导出对照在 `storage/`，曲线首次绘制及切换在 `curve-open/`，播放状态在 `runtime/`。导出修复的源文件与成品缓存数据分别位于 `open-save-review/source-version/` 和 `open-save-review/export-cache/`。
