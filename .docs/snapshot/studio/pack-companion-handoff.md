# Pack 输出变更：Engine / SDK 业务交接

核对基线：`6c8c691`。更新日期：2026-10-19。

Studio 已完成新的 Pack 导出形态：执行内容与名称映射分离，每个 Action 包包含完整嵌套执行内容，游戏侧可以按需使用独立包。本次仅变更 Studio，Engine / SDK 及其示例尚未完成对应接入。

本文说明已确定的产品约定、需要跟进的功能和验收预期。Engine / SDK 的接入方案、接口设计和实现方式由各自负责方确定。

## Studio 已确定的输出约定

### 每包独立的最小映射

| 输出 | 承载内容 |
|---|---|
| `Init.bytes` | 全部 Variable 执行定义、Label 身份与数值锚点，以及总线等公共执行内容。 |
| `Init.json` | Variable 与所属有名称 Label 的名称—GUID 映射。 |
| `Action名称.bytes` | 根 Action 及其完整嵌套执行内容，包括所需可播放对象与媒体。 |
| `Action名称.json` | 该根 Action 的名称—GUID 映射。 |

Action 伴随内容示例：

```json
{
  "name": "Play_Footstep",
  "guid": "33333333-3333-3333-333333333333"
}
```

Init 伴随内容示例：

```json
{
  "variables": [
    {
      "name": "Surface",
      "guid": "11111111-1111-1111-1111-111111111111",
      "labels": [
        {
          "name": "Stone",
          "guid": "22222222-2222-2222-2222-222222222222"
        }
      ]
    }
  ]
}
```

`.bytes` 不包含 Action、Variable、Label 名称。名称、说明、单位、显示精度等非执行信息的变化，不改变执行 bytes 或执行版本。无名称的 Label 仍保留执行身份和数值锚点，但不出现在名称映射中；伴随文件不是全部 Label 的清单。

JSON 只承载上述最小映射，不增加说明、展示属性、执行参数、平台发现字段、版本、hash 或项目目录。导出不再提供总索引、manifest、全项目 Action 表和编辑器波形元数据。伴随文件用于名称映射，不承担全项目包发现职责。

Action 文件继续按名称命名，不使用 GUID 文件名。GUID 表示对象身份，名称文件名用于定位输出，两者不能互相替代。调用方明确指定平台目录，语言保持现有子目录结构。

### 嵌套内容随父包交付

对于 `A → B → C`，A 包包含 A、B、C 的执行定义及所需资源；B 包包含 B、C；C 包包含 C。准备 A 只需要 A 包及适配的 Init，不要求 B、C 的独立包存在。Action 包之间不再存在独立文件依赖。

B、C 可以各自独立导出。取消 B 的独立输出，不会截断 A 内的 B；嵌套内容缺少所需语言资源时，A 仍不能成功导出。父包的语言变体包含对应语言的完整嵌套内容。

`A.json` 只映射 A，不额外列出 B、C。A 内能够执行 B，不代表 B 的名称已经作为独立入口可用。

### 选择导出与历史文件

Studio 严格按右键选择或 Export Checked 的根包范围导出，不自动重建未选父包或子包。只更新 B 后，历史 A 仍可能内嵌旧 B；只更新 A 后，独立 B 包也可能保持旧内容。单包导出成功不表示磁盘上的所有包已同步为同一批次，未选历史包的版本差异也不阻止本次导出。

右键只导出 Action 时保留已有 Init，Action 仍记录按当前工程生成的真实 Init 版本与总线要求。旧 Init 可能不满足新 Action 的要求。Export Checked / Export All 会按当前工程生成或复用 Init；当前 Init 系统行不提供独立选择导出。

完整导出关闭自动清理时保留历史 bytes / JSON 对；开启时按原有范围清理不再使用的输出。右键选择性更新保留未选文件，不因清理开关扩大范围。旧名和新名可能同时留在目录中，因此目录内所有 JSON 不能被视为同一份当前发布清单。

## Engine 需要跟进的功能

| 功能领域 | 预期业务行为 |
|---|---|
| 新输出可执行 | 新导出的 Init 与 Action 可以正常加载、发声；Variable、Label、绑定和总线的执行语义保持正确。名称从二进制移出后，这些能力仍完整可用。 |
| 按名称与 GUID 使用对象 | Action、Variable、Label 都能按所属包提供的映射使用名称，同一对象的名称调用与 GUID 调用结果一致。Label 名称以所属 Variable 为范围。 |
| 包与名称的一致性 | 包内容、对象身份、名称及所属关系保持一致。单份映射内的重复项，以及缺失、损坏或不匹配的映射应明确报错；失败后原有可用内容和名称不受破坏，不出现只更新其中一部分的状态。 |
| 加载、替换与卸载 | 名称的可用范围随所属包变化。卸载后不遗留无主名称；替换成功后使用新内容和新名称，失败后仍能继续使用原状态。 |
| 改名 | Action、Variable、Label 仅改名且 bytes 不变时，新名称仍能生效，旧名称不再指向当前对象。旧名称查询结果或已失效引用不能继续造成误调用。Label 改名不改变其执行锚点。 |
| 嵌套对象的共同使用 | A 内嵌 B、独立 B 也被加载时，相同 GUID 且内容一致的对象可以共同使用。卸载其中一个包不影响另一个包；替换一个包不应暗中改变另一个包承诺的执行内容。 |
| 版本与依赖冲突 | 实际加载的包中，同 GUID 不同执行内容、Init 不满足 Action 要求等冲突应明确拒绝，并保留原有可用状态。磁盘上未使用的历史包不影响当前加载。 |
| 平台与语言 | 使用请求的平台与语言对应内容。不同语言可能具有相同 Action 名称和 GUID，这不代表其执行内容可互换；错误组合不能被静默接受。 |
| 录制与重放 | 现有录制、重放能力能正确还原名称调用、改名、包替换、卸载及失败后的状态，结果与原始使用过程一致。 |

运行时名称能力应随实际使用的包增长。加载或使用一个 Action 不以准备全项目名称表为前提，也不应重新引入旧的全项目 Action 数量限制。

新输出不提供历史别名、退役名称记录或全项目发布完备性证明。依赖这些信息的旧能力，以及旧包和旧录制内容的兼容范围，需要 Engine 负责方明确说明，不能将缺失信息表现为已经验证通过。

## SDK 需要跟进的功能

| 功能领域 | 预期业务行为 |
|---|---|
| 项目启动 | 使用调用方指定的平台目录和语言设置，能够基于新输出完成初始化，不再依赖总索引或全项目 manifest。 |
| 按需准备与播放 | 游戏按 Action 名称即可定位对应名称文件，准备完成后能够播放。嵌套执行无需额外提供子 Action 独立包；启动和单次准备不要求遍历或预加载全项目包。 |
| 名称调用的使用边界 | 对“准备并播放”和“调用已准备对象”的行为、完成时机和失败原因有清晰约定。名称解析本身不代表资源已准备完成。Action、Variable、Label 的名称能力均在接入范围内。 |
| 包的更新与释放 | 加载、替换、卸载和名称变化在游戏侧表现一致。加载冲突或资源获取失败能够反馈给调用方，并保持原有可用状态。 |
| 多种资源交付方式 | 现有文件加载、Unity 资源、自定义资源来源和移动平台交付方式能承接新输出，平台、语言、按需准备和失败行为保持一致。 |
| 编辑器与符号能力 | 已有对象选择、引用配置及代码符号生成功能能够使用新的名称—GUID 映射。Variable 的类型和执行一致性检查仍有效，不因 JSON 只含名称而丢失。 |
| 试听与展示信息 | 现有 Action 试听需要适配新包。导出已不再提供波形、源时长和候选源信息，相关展示功能的可用范围需明确，不将缺失信息呈现为有效数据，也不能要求游戏运行时依赖 Studio 创作工程或源素材补足这些信息。 |
| 既有项目与示例 | 已有场景、资源引用、启动配置、示例和集成验证内容需要跟进新输出。旧使用方式的兼容或迁移范围应向使用方说明。 |

编辑器可以有面向用户的内容浏览能力，但其浏览结果不能默认证明目录里的所有历史文件均为当前可用内容，也不能因此要求游戏运行时依赖一个新的总表。

SDK 的便利功能不应反向扩大 Studio 的最小导出集合。需要执行参数的功能不能假定这些参数仍存在于名称 JSON；需要全局历史信息的功能也不能假定新输出仍提供该信息。

本次对 Unity SDK 的现有使用流程做了核对。其他宿主 SDK 的覆盖范围和原有未完成能力需要各自说明，避免将既有缺口归因于此次输出调整。

## 共同验收场景

| 场景 | 验收预期 |
|---|---|
| 只准备 Init | Variable 与有名称 Label 的按名能力可用，不要求全项目 Action 预先可见。 |
| 只提供 Init 与 A，A 嵌套 B、C | A 能完整执行，无需 B、C 独立文件；未单独准备的 B、C 不因内嵌而自动成为按名入口。 |
| 同一对象分别按名称和 GUID 使用 | 指向同一已准备对象，执行结果一致。 |
| 只改 Action、Variable 或 Label 名称 | bytes 不变时仍能更新名称；旧名失效，执行身份和语义保持不变。 |
| A 与独立 B 同时使用相同内容 | 卸载任一包不影响另一包需要的对象；相同 GUID 的不同内容被明确拒绝，原状态保持可用。 |
| 只更新所选 Action，保留旧父包、子包或 Init | 未选输出保持原状；实际准备不兼容组合时明确失败，不静默混用或替换内容。 |
| 文件缺失、映射错误或更新失败 | 不出现内容已变而名称未变等不一致状态，之前可用的内容仍可继续使用。 |
| 平台、语言或资源来源发生变化 | 使用指定内容，错误组合有明确反馈；文件、Unity 资源、自定义来源和移动平台行为一致。 |
| 工程中未使用的 Action 数量大幅增加 | 启动和单个 Action 的准备不因此需要读取全项目名称映射或预加载全部包。 |
| 录制后经历改名、替换和卸载，再重放 | 对象身份、名称可用性、执行结果和失败后的状态与录制时一致。 |

验收内容应来自真实 Studio 工程的正常导出，覆盖播放、Variable / Label、平台、语言和嵌套 Action，并保持原有对象身份。示例及验证资料需要反映实际可用能力；尚未通过的阶段不能视为接入完成。

## 已有证据与待完成验证

用户提供的 Wwise 2024.1 auto-defined 样本中，父 Event 的 bank 已包含被调用子 Event 的执行内容；Unity 集成按父 Event 名称准备对应 bank。Windows / Android、英语 / 中文四组生成物结论一致。这支持“嵌套执行内容随父包交付”的业务形态。Wwise 的伴随 TXT 同时列出了父子 Event，Harken 已确定采用仅映射根 Action 的最小伴随，两者不要求格式相同。本轮未另行运行 Wwise 播放验证，样本在 Unity 发声由用户确认。

2026-10-19，Studio 与测试程序构建成功。相关测试共 201 例，196 例通过，5 例失败，0 例跳过。

Studio 的选择性更新完整流程、旧输出清理、构建计划、平台迁移和嵌套闭包导出已通过。普通嵌套 Action 只加载 Init 与父包的场景，也已通过真实 Engine 激活与执行。

剩余 5 例均受阻于现有 Engine 对新 Variable 执行数据的支持。以下场景的后续业务行为仍待完成验证：

- 共享绑定下的多包播放与版本冲突处理。
- 导出包加载后绑定身份的可用性。
- 替换包缺少绑定定义时保留原状态。
- Init 中 Variable 定义与 Action 需求的配合使用。
- 仅更新选定 Action 后的原生激活。

这些场景均未通过激活，不能据此认为后续播放、替换和恢复行为已经通过。伴随名称能力、含 Variable 的完整发声、SDK 启动及包生命周期仍需完成接入验收。
