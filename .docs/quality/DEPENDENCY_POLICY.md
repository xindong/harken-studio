# 第三方依赖政策

本文档是仓库第三方依赖治理的正文标准：定义许可证准入、引入登记与发布义务规则。`NOTICE` 只声明分发物实际包含的第三方内容；未随附的开发、测试、CI 依赖不列入，源码包和二进制包分别按各自内容确定范围。自动化检查见 [compliance-rules/COMPLIANCE_AUDIT_RULES.md](compliance-rules/COMPLIANCE_AUDIT_RULES.md) 的 `LIC` / `DEP` 系列规则。

## 许可证准入

| 闭包 | 准入范围 |
| --- | --- |
| 运行时 / SDK / 随游戏发行的依赖闭包（`HarkenEngine`、`HarkenSDK` 及其传递依赖） | 仅宽松许可证：MIT、MIT-0、BSD、Apache-2.0、zlib、公有领域等 |
| Studio 前端（`HarkenStudio` 子树，不进入运行时闭包） | 宽松许可证之外，允许弱 copyleft（LGPL 等），必须同时记录链接方式与发布义务 |
| Hub（`HarkenHub` 子树，不进入运行时闭包） | 同 Studio 前端 |
| 任何产品闭包 | GPL / AGPL 禁止 |
| 测试与开发工具（不随产品分发，如 GoogleTest、Python 工具依赖） | 宽松许可证；不得进入任何发布闭包 |

## 引入与升级要求

1. 固定精确版本或完整 40 位 commit SHA；`FetchContent` 下载归档必须使用 `URL_HASH SHA256` 或等价内容完整性校验；
2. 对实际分发的依赖，在对应 `NOTICE` 登记名称、精确版本/commit、许可证、用途、获取方式与本地路径；未分发依赖保留在开发依赖配置及相关文档中。
3. vendored 依赖必须保留上游 `LICENSE` / `COPYING` / `NOTICE` 等许可证证据文件；许可证全文嵌入单文件源码时，`NOTICE` 必须明确记录该文件路径；
4. 弱 copyleft 依赖必须在对应分发物的 `NOTICE` 记录链接方式（静态/动态）；静态链接的，必须同时记录发布前需完成的义务。LGPL-2.1 §6(a) 允许通过对应的完整应用源码、库源码及构建文件支持用户修改库后重新构建，也可按适用条款提供可重新链接的目标文件；不能将缺少目标文件单独判定为违规。两种方式均须保留许可证文本并满足适用条款；
5. 依赖的编译能力范围应与项目公开声明一致，不得静默启用声明之外的能力。

## 发布义务

- "公司内部"不自动豁免跨团队、关联公司或合作方分发的许可证义务；
- 发布前须逐项核对实际分发内容与对应的许可证/NOTICE 文本一致；
- 二进制分发包应随附对应闭包的第三方许可证与归属声明文本。
- 每次打包为 Hub、Studio、SDK 产物生成 SBOM 和核验记录，保留代码提交号、依赖版本和来源、构建信息及产物哈希，不自动下载或归档源码。正式发布时另行准备并提供适用许可证要求的对应源码和构建材料；相同版本的第三方源码可复用。自动检查结果不替代源码交付、人工权属审查、全量扫描和发布批准。

## 例外

政策例外必须经法律审查批准，并在对应依赖记录中保留批准依据与适用范围；无书面例外记录时，一律以本文档为准。
