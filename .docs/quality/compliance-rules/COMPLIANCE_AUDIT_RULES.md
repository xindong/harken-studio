# 合规巡检规则目录

本文档是 Quality 体系中合规巡检规则的人类可读标准。脚本实现位于
`.scripts/compliance_audit.py`；规则新增或调整时，应同步更新本文档和脚本。

## 覆盖边界

- 默认文件集合以 `git ls-files` 为准，检查当前提交中的完整已跟踪树；PR 专属治理规则另以目标分支 base SHA 中的 PR 模板及 PR 描述为输入。
- 覆盖根目录、`.github/workflows/`、工程源码、构建脚本、文档、vendored 第三方代码和第一方非代码资产。
- 文本内容扫描覆盖工程中常见源码、配置、构建、项目文件、HTML/CSS/JavaScript、SVG 和文档后缀；单文件上限为 10 MB。
- 提交内容中的凭证字符串不属于自动巡检范围；`SEC-002` 继续检查产品代码的凭据存储行为。
- 未跟踪/已忽略文件、Git 历史、构建产物、远程依赖下载后的完整内容和最终安装包不在 GitHub 定期巡检的文件范围内。它们需要在发布前另做历史密钥扫描、依赖/SBOM 扫描和安装包核验。
- “完整已跟踪树”只描述文件集合；每条规则仍有自己的适用对象。巡检是发布门禁证据之一，不替代律师审查、隐私影响评估或人工许可证判断。

## 风险等级

| 等级 | 使用口径 |
| --- | --- |
| 严重 | 已确认会阻断开源/商业发布，或可能直接造成违法、重大侵权、真实密钥泄露。 |
| 高 | 发布前必须处理或形成书面豁免的问题，例如许可证缺失、隐私/遥测高风险、来源记录缺失。 |
| 中 | 发布前需要评估和尽量整改的问题，例如供应链完整性不足、构建信息泄露、权利记录不充分。 |
| 低 | 不一定阻断发布，但会影响声明准确性、最小化原则或长期维护质量。 |
| 信息 | 本地状态提醒，不代表仓库本身已不合规。 |

## 主题分类

| 主题 | 覆盖范围 |
| --- | --- |
| 授权与来源 | 项目许可证、第三方依赖声明、历史代码/资产来源和权利记录。 |
| 隐私与数据处理 | 运行时遥测、外部数据流、设备/账号标识、隐藏持久化、构建身份、对话记录等个人信息或敏感数据处理。 |
| 发布边界与私有资料 | 个人自动化、本地工作流、私有状态目录是否应进入公开仓库。 |
| 供应链与第三方依赖 | 依赖下载固定、哈希校验、依赖能力范围与声明一致性。 |
| 仓库治理 | PR 描述是否保留目标分支模板的完整骨架；PR 引入的 commit 是否带有效 DCO trailer。 |
| 密钥与本地配置 | 产品凭据存储行为、本地配置状态。 |

## 当前规则

| 规则 ID | 等级 | 主题 | 检查标准 |
| --- | --- | --- | --- |
| `LIC-001` | 高 | 授权与来源 | 根目录必须存在项目自身许可证文件，例如 `LICENSE`、`LICENSE.md` 或 `COPYING`。 |
| `LIC-002` | 高 | 授权与来源 | 每个已跟踪 vendored 依赖必须在根目录 `NOTICE` 登记名称、精确版本/commit、许可证、用途、获取方式和本地路径。 |
| `LIC-003` | 高 | 授权与来源 | 每个已跟踪 vendored 依赖必须保留 `LICENSE`/`COPYING`/`NOTICE` 等许可证证据；单文件内嵌许可证时，根目录 `NOTICE` 必须明确记录文件路径。 |
| `LIC-004` | 严重/高 | 授权与来源 | 运行时、集成包和随游戏发行的依赖闭包只允许宽松许可证；Studio 的弱 copyleft 依赖必须记录链接方式和发布义务；GPL/AGPL 禁止进入任何产品闭包。 |
| `TEL-001` | 高 | 隐私与数据处理 | 产品/演示可执行程序不得包含运行时 telemetry 开关、target、源码树、启动入口或通知路径；版本追踪只允许通过构建期二进制文件属性实现。 |
| `TEL-002` | 高 | 隐私与数据处理 | 程序启动阶段不得触发 telemetry 入口；不得保留 `--enable-telemetry`、`harken_host telemetry` 或类似运行时参数。 |
| `TEL-003` | 高 | 隐私与数据处理 | 不得采集稳定设备或账号标识，例如 MachineGuid、Windows SID、本地 IP、第三方账号标识、用户名、主机名或邮箱。 |
| `TEL-004` | 高 | 隐私与数据处理 | 不得将 telemetry 记录写入隐藏或系统属性文件。 |
| `TEL-005` | 高 | 隐私与数据处理 | 不得将 telemetry 记录写入 NTFS 备用数据流等不透明位置。 |
| `TEL-006` | 高 | 隐私与数据处理 | 不得将 telemetry 记录写入注册表缓存等不透明位置。 |
| `PRIV-001` | 中 | 隐私与数据处理 | 面向发布的构建产物不得嵌入本地主机名、用户名等个人环境信息。 |
| `DEP-001` | 中 | 供应链与第三方依赖 | `FetchContent` 下载归档必须使用 `URL_HASH SHA256` 或等价内容完整性校验。 |
| `DEP-002` | 低 | 供应链与第三方依赖 | vendored 依赖的编译能力范围应与项目声明一致。 |
| `DEP-003` | 低 | 供应链与第三方依赖 | 文件加载器实际支持的格式必须与公开声明一致，或限制为声明范围内的格式。 |
| `DEP-005` | 中 | 供应链与第三方依赖 | 任意第一方 `CMakeLists.txt`/`.cmake` 中通过 `FetchContent` 获取 Git 仓库时，`GIT_TAG` 必须固定到完整 40 位 commit SHA。 |
| `SEC-002` | 高 | 密钥与本地配置 | API key、token、密码等凭据不得明文或仅 Base64 写入 `QSettings`、INI 等普通配置；必须使用操作系统凭据保险库/用户绑定加密，或仅保留在进程/会话内。 |
| `GOV-001` | 高 | 仓库治理 | PR 描述必须保留目标分支 `.github/PULL_REQUEST_TEMPLATE.md` 的全部二级章节，且每个章节的勾选项条数不得少于模板。模板挂在条目下的 `>` 说明行是勾选后才需回答的提示，未勾选条目可以不保留，其回答义务由 `GOV-002` 按条目判定。判定不依赖条目文案：允许只保留中文或只保留英文、允许调整章节顺序、允许改变标题级别、允许改写措辞；但不得删减条目，以便评审者在描述中看到完整的待确认项。不得用 PR 修改后的模板改变判定标准。 |
| `GOV-002` | 高 | 仓库治理 | PR 描述的必答内容不得留空：无勾选项和填写项的章节正文必须有内容；多选章节至少勾选一项，确认类章节（提交前检查）必须逐条全部勾选；填写项必须在冒号后或紧随其后的续行给出内容；已勾选条目若自身以冒号结尾，或模板为该条目声明了 `>` 说明行，必须逐条补齐说明内容。说明行是否已作答按模板提示文案判定：扣除提示文案后仍有实质内容才算已填写，原样保留提示（含只保留其中一种语言）视同未填写，作答不要求写成冒号后缀。 |
| `GOV-003` | 低 | 仓库治理 | PR 描述的条目文案应与模板语义一致。该项按双语别名做尽力匹配，仅在条数校验通过后提示评审者人工核对措辞是否被改写，不作为阻断条件。 |
| `GOV-004` | 高 | 仓库治理 | PR 引入的 `base.sha..head.sha` 范围内，每个非 merge commit 必须有行首 `Signed-off-by: Name <email>`（冒号后一个空格，多出来的空格进 name、不 trim；行长超过 512 或姓名捕获超过 256 的行跳过；trailer 捕获的 email 必须像邮箱）。不要求 name+email 等于 author 或 committer。模板 DCO 勾选不能替代 trailer。父提交数大于 1 的 merge commit 豁免；看起来像 bot 的邮箱不豁免。head.sha 缺失、`git log` 失败或范围为空时失败关闭，不当成已全部签署。 |
| `LOCAL-001` | 信息 | 密钥与本地配置 | 本地 gitignored 配置存在时只作为提醒；不得提交、打包或发布。 |
| `LOCAL-002` | 信息 | 发布边界与私有资料 | 本地未跟踪自动化目录存在时只作为提醒；不得默认进入发布范围。 |

## PR 专属治理输入

`GOV-001`、`GOV-002`、`GOV-003` 和 `GOV-004` 只在 `pull_request` 事件运行。workflow 监听 `opened`、`synchronize`、`reopened` 和 `edited`；脚本从 GitHub event payload 读取 `base.sha`、`head.sha` 和 PR `body`。

前三条规则必须用 `git show <base>:.github/PULL_REQUEST_TEMPLATE.md` 读取目标分支模板；checkout 中的模板属于 PR head，不可作为自身合规标准。PR event、base SHA 或 base 模板缺失、无效、不可读取时扫描失败关闭。`GOV-004` 用 event 的 `base.sha..head.sha` 读取 commit trailer，不使用 checkout `HEAD` 代替 head。head.sha 缺失或非法时仍校验描述规则，并对 `GOV-004` 给出高风险 finding。定时、手动触发和 `main` push 不具备 PR 上下文，因此跳过这四条规则。

章节与条目要求全部由 base 模板结构推导，不在脚本中硬编码章节名或条目文案；模板增删条目后，判定基准随之变化，此前已开启的 PR 需要按新模板补齐条目。

## 发布前人工门禁

以下项目不能仅凭当前静态巡检自动判定，正式开源或商业发布前必须保留人工证据：

1. 对实际分发内容及其对应的许可证/NOTICE 做逐项核对，并确认 QtADS 等弱 copyleft 义务已满足。
2. 对完整 Git 历史做 secret 扫描和必要的密钥轮换；此项独立于本自动巡检执行。
3. 为解析后的依赖生成 SBOM，并执行漏洞、恶意包和许可证数据库扫描；当前巡检不下载或解析远程依赖内容。
4. 核验最终安装包、符号、资源、示例、调试信息和自动化目录的发布边界，不以“仓库中已跟踪”自动等同于“允许随产品分发”。
5. 对 `.docs/quality/DATA_FLOW_INVENTORY.md` 做隐私影响评估，核对真实请求载荷、第三方处理条款、用户告知/同意、留存和删除行为。
6. 由权利人或法律顾问确认第一方资产、历史内部代码和公开公式的权属证据；自动化只能检查记录是否存在，不能判断授权是否真实充分。

## 新增规则流程

1. 在本文档新增规则条目，先确定 `规则 ID`、等级、主题、检查标准和处理建议。
2. 在 `.scripts/compliance_audit.py` 中新增或调整 `rule_<name>` 函数。
3. 在 `run_audit()` 中调用新规则函数。
4. 每个 finding 至少包含规则 ID、风险等级、分类、标题、说明和建议；能定位文件时补充文件和行号。
5. 本地运行：

```powershell
python .scripts/compliance_audit.py `
  --json-out .temp/compliance/compliance-report.json `
  --markdown-out .temp/compliance/compliance-report.md
```

## 维护原则

- 规则文档面向报告阅读者，使用中文。
- 文件名、代码符号和规则 ID 保持原样，便于工程定位和自动化对比。
- 新规则默认扫描完整已跟踪代码树，不做 diff-only 检查。
- 规则不得读取或输出真实 secret 值；证据中如可能包含密钥，必须脱敏。
